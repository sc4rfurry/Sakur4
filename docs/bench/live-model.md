# Live-model A/B: does a real model benefit

Every other benchmark in this repository measures the engine. This one measures a
**model** — whether a locally running 27B model, driven through a real harness, actually
benefits from the memory layer, and whether the plumbing that was supposed to deliver it
actually delivers it.

## Setup

| | |
|---|---|
| Harness | Oh My Pi 18.2.0, the `omp-sakur4` extension |
| Model | a locally served 27B model at Q3_K, 81,920-token window |
| Repo | A three-file fixture whose contents deliberately say **nothing** about the question |
| Question | *"What is the one rule about the migrations directory in this project? Answer in one short line, or say UNKNOWN."* |

The fixture matters. If the answer were discoverable by reading the repository, a correct
answer would prove nothing. `README.md` says in as many words that nothing there mentions
migrations — so the only possible source of a correct answer is Sakur4.

## The result

Three arms, same question, same directory, same model. Only the plugin and the store differ.

| Arm | Plugin | Store | Answer |
|---|---|---|---|
| **A** | active | holds the constraint | **"Migrations are generated by `scripts/gen.sh` — never edit anything under `migrations/` directly."** |
| **B** | **disabled** (`--no-extensions`) | holds the constraint | *"UNKNOWN — the repo (README, `src/db.rs`, `src/parser.rs`) contains no mention of a migrations directory…"* |
| **C** | active | **empty** | *"UNKNOWN — the repo has no migrations directory and no file states a rule about one…"* |

**Arm B is the control that makes this meaningful.** It had the *same populated store* as
arm A and still answered UNKNOWN, because the plugin was off. Arm C isolates the other
variable: plugin on, nothing to inject, UNKNOWN again.

So the correct answer is attributable to the plugin, to the store contents, and to both
being present. Nothing else in the setup differs.

## Why arm A should have failed

This is the point of running it. Until round 2 of the current work, the extension **never
injected the Anchor Set** — its context hook called `memory.recall` and nothing else. A
short rule like *"never edit anything under `migrations/`"* matches almost no query, so it
was absent from most turns.

Arm A is the same experiment that would have produced **UNKNOWN in all three arms** before
that fix. The bug was in the live path only: the engine kept anchors out of eviction
correctly, and the README's claim that pinned content is "rendered verbatim into every
prompt" was true of the engine and false of the only place a user can see it.

## Does the model *use* the tools? Now answered: no, not when the hook suffices

Asking the model to "search your Sakur4 memory … use the `sakur4_recall` tool" for a
uniquely-named fact returned it correctly in 50.1s. That run could not distinguish the
model **choosing** to call the tool from the retrieval hook **injecting** the fact.

The extension now counts both, so a session can be classified after the fact:

```
session summary {"toolCalls":0,"retrievals":1}
```

**The model did not call the tool.** It answered correctly from what the context hook had
already injected. Both paths produce the same user-visible result, and they are not the
same finding:

- `retrievals > 0, toolCalls == 0` — the hook supplied the context and the model used it.
  **This is the intended design.** The point of injecting is that the model should not have
  to know it needs to search.
- `toolCalls > 0` — the model decided on its own that memory was missing something. That
  is what `sakur4_recall` exists for, and it is the case the hook cannot cover, because the
  hook only injects what the *current prompt* resembles.

One prompt is not a behavioural study. What it does establish is that the answers in the
table above came from injection rather than from tool use — which is the honest reading of
the earlier result, and the reason the counter was added at all.

## Cost, which is why the arms are short

Each OMP invocation against this server costs **25–95 seconds** — the harness sends a
large system prompt and the local model prefill-runs at roughly 1,100 tokens/second, which
`docs/verification/` measured independently. A 20-turn A/B would take about 45 minutes per
arm and would add little: the question above is decided in one turn.

That is also why `docs/bench/ab.mjs` uses a scripted driver. It measures the context and
memory layer at 200 turns for the cost of a few round trips. **The two benchmarks are
complementary and neither substitutes for the other:**

| | `docs/bench/ab.mjs` | this |
|---|---|---|
| Turns | 205 | 3 |
| Measures | tokens sent, compaction, recall mechanics | whether a model benefits |
| Cost | seconds | minutes |
| Model in the loop | no | yes |

## Reproducing

```bash
# A daemon is not required: the extension starts one, or uses SAKUR4_BIN.
export SAKUR4_BIN=~/.cargo/bin/sakur4d
export SAKUR4_DB=/tmp/ab-live.db

# Plant the constraint into the session the extension will query.
# The session id is derived from the working directory, so run from the fixture.
cd /tmp/live-ab-repo
node skills/sakur4/scripts/sakur4.mjs pin --kind safety_constraint \
  --content "NEVER edit anything under migrations/ directly; migrations are generated by scripts/gen.sh"

# Arm A
omp -p "What is the one rule about the migrations directory in this project? Answer in one short line, or say UNKNOWN." \
    --model local/<model> --thinking off --no-session --no-lsp --no-skills

# Arm B — the control
omp -p "What is the one rule about the migrations directory in this project? Answer in one short line, or say UNKNOWN." \
    --model local/<model> --thinking off --no-session --no-lsp --no-skills --no-extensions

# Arm C — plugin on, empty store
SAKUR4_DB=/tmp/empty.db omp -p "…" --model local/<model> --thinking off --no-session --no-lsp --no-skills
```

## What is still not verified

- **No multi-turn session has been run.** These are single-turn probes. Whether the model
  behaves differently at turn 100, after several compactions, is untested — OMP's own
  compaction can be forced with a deliberately small window, and that is the next
  experiment worth running.
- **Model-initiated tool use is unproven.** In the one case measured it did not call the tool, because injection had already answered the question. Whether it calls `sakur4_recall` when the hook *cannot* help is untested.
- **Hermes has never been driven by a live model**, only its transport and its
  ContextEngine interface. The OMP extension is the only harness with a live-model result.
